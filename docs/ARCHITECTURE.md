# 架构与关键设计取舍

## 1. 总体形态：一主一辅的「云边协同」

```
云端主控（Linux, systemd）                    边缘 GPU 节点（Windows, 计划任务）
─────────────────────────                    ───────────────────────────────
main.py watch                                src/edge_worker.py  (:18088)
 ├── 定时巡检线程（默认 30 分钟）               ├── GET  /health     探活
 │    └── 多账号独立画像：检索→闸门→转写→提炼→推送  └── POST /transcribe 转写（子进程跑 Whisper）
 └── 实时监听线程（轮询 6s）
      ├── 私信指令（查看设置 / 设置关键词 / 设置风格 / 监控UP …）
      ├── 私信分享视频 → 即时总结
      └── 评论区 @ 触发 → 即时总结
```

两端代码同源：`src/` 下 13 个模块完全共用，边缘侧只是**多了一个 HTTP 服务壳**（`edge_worker.py`）与本地转写实现（`transcriber.py` / `worker.py`）。这样修一处逻辑，两端行为一致。

## 2. 为什么要有边缘节点

| 维度 | 本地 GPU 转写 | 云端 ASR / 视觉 |
|---|---|---|
| 速度 | faster-whisper large-v3-turbo，无网络上传 | 需上传音频/帧，受限带宽 |
| 成本 | 电费 | 按量计费的多模态 API |
| 可用性 | 只在 PC 开机时 | 7×24 |

**结论**：PC 在线时用它，离线时无缝降级——两者不是二选一，而是一条降级链。

```
本地 GPU 转写 ──探活失败(0.8s)──► 云端音频 ASR ──无人声──► 云端抽帧视觉描述 ──失败──► 待补推队列
```

## 3. 关键设计取舍

### 3.1 常驻轻、重活外包（内存纪律）

云端主控常驻内存约 **90MB**；边缘节点常驻约 **80MB**。

Whisper 的 GB 级内存**跑在子进程里**（`worker.py`），任务结束进程退出即归还 —— 这是刻意设计：常驻进程一旦自己加载模型，几十小时巡航后内存就成了隐患。

### 3.2 边缘取流而非云端传流

B 站音频 URL 带 **IP 绑定签名**：云端取到的直链，到边缘机下载常被 403。

所以 `transcribe` 请求里带的 URL 仅作**白名单兜底**，边缘节点优先用**本机 cookie 重新取流**。同时严格限制可下载域名（`.bilivideo.*` / `.bilibili.com` / `.hdslb.com` 等），**绝不下载任意 URL**（防 SSRF）。

### 3.3 相关性闸门与「防圆谎」护栏

两道防线，目的都是**不让错误内容冒充正确内容**：

1. **相关性闸门**：检索回来的视频先过关键词 + 语义双重筛选，不合格直接丢弃；
2. **防圆谎护栏**（`summarizer.py`）：当转写文本与视频主题明显失配（例如拿到的是别的视频的字幕），模型很容易「顺着编」出一条看似合理的总结。护栏会检测这种失配并**显式标记**，而不是让它悄悄通过。

### 3.4 字幕通道默认关闭

实测（同一 `bvid+cid` 连查多次、结果各不相同）：B 站字幕接口返回的正文约 **75% 属于其它视频**。

唯一能拦住它的是上面那道闸门，但收益极低（有本地 GPU 时根本走不到这里），风险不低。故 **显式关闭**，降级链变成「要么真内容，要么老实排队」（`cloud_mm.subtitle_channel: false`）。

### 3.5 诚实降级

`pending_notice: true` 时，取不到真实内容会发一条**明确标注「待补推」**的通知，而不是用标题和简介编一份空壳摘要糊弄用户。宁可承认失败，也不污染信噪比。

### 3.6 去重与限速

- 去重：SQLite `data/history.db` 记录已处理 BV 号，重启不丢；
- 限速：`max_push_per_keyword`（每次巡检每关键词最多 1 条）、`max_chunk_size`（单条私信 700 字）、`send_interval`（推送间隔 2s）—— 保守优先，避免刷屏与风控。

## 4. 数据流

```
① 巡检：
   关键词检索 / UP 主上新
     → 相关性闸门（filter.py）
     → 去重（storage.py）
     → 取内容：边缘 GPU 转写 ／ 云端 ASR ／ 云端视觉
     → LLM 提炼（summarizer.py，带失配护栏）
     → 分片推送（notifier.py，多账号按各自画像）
     → 落库（history.db）＋ 归档（summaries/）

② 交互：
   私信/评论通知（bot_listener.py，轮询 6s）
     → 指令解析（配置热重载）／ BV 号识别
     → 即时总结 → 单独回发给发起账号
```

## 5. 模块职责一览

| 模块 | 职责 |
|---|---|
| `pipeline.py` | 主流水线编排；云边路由决策 |
| `bili_api.py` | B 站接口（cookie、UA、风控重试、WBI 签名） |
| `bot_listener.py` | 私信 / @ 监听、自然语言指令解析、配置热重载 |
| `filter.py` | 相关性闸门 |
| `summarizer.py` | LLM 提炼 + 失配护栏 |
| `notifier.py` | 分片推送与限速 |
| `cloud_mm.py` | 云端多模态（音频 ASR、抽帧视觉描述） |
| `transcriber_client.py` | 云边混合路由（探活 0.8s + 降级） |
| `transcriber.py` / `worker.py` | 本地 faster-whisper 转写（子进程隔离） |
| `edge_worker.py` | 边缘 HTTP 服务（`/health`、`/transcribe`） |
| `audio.py` | 取流、转码 |
| `storage.py` | SQLite 去重与历史 |
| `config_loader.py` | 配置加载与校验 |
| `tools/` | 运维：每日自检、体检报告、推送上屏复核 |
